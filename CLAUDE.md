# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

**Bookmarkify** (书签鸭) is a bookmark management platform consisting of four services that work together. Each service has its own `CLAUDE.md` with detailed conventions — read those when working inside a specific service.

## Services

| Directory | What it is | Port | Tech |
|---|---|---|---|
| `bookmarkify-api/` | Backend REST API + WebSocket server | 8001 (local) / 7001 (prod) | Kotlin 2.1 + Spring Boot 3.5 |
| `bookmarkify-web/` | User-facing frontend | 3000 | Nuxt 4 + Vue 3 + TypeScript |
| `bookmarkify-scrapper/` | Headless page-scraping microservice | 3000 | Rust (axum + spider-rs) |
| `bookmarkify-admin/` | Admin panel (pruned Vben Admin, web-ele only) | 5777 | Vue 3 + Vite |

## Quick Start Commands

### API (bookmarkify-api)
```bash
cd bookmarkify-api
./gradlew bootRun --args='--spring.profiles.active=dev'   # run
./gradlew bootJar                                          # build jar
./gradlew test                                             # run tests
```

⚠️ **The `dev` profile connects to the production database** (`.env` supplies the host), and therefore runs with `bookmarkify.scheduling.enabled=false` — no liveness sweeps, no reconciliation, no log purge, no OSS reconcile. Without that switch a local run adds a second set of cron jobs writing to the live database; it has actually happened. The visible consequence is that **bulk import never completes locally** (`drainStuckLoading` is its only consumer, so tiles spin forever with no error). To exercise those paths, point the datasource at a local database first, then pass `--bookmarkify.scheduling.enabled=true`.

### Web (bookmarkify-web)
```bash
cd bookmarkify-web
pnpm install
pnpm dev        # http://localhost:3000 — needs API on :8001
pnpm build
```

### Scrapper (bookmarkify-scrapper)
```bash
cd bookmarkify-scrapper
cargo run -p scraper-service                               # run
cargo build -p scraper-service --release                  # build
cargo test -p scraper-service                             # unit tests
cargo test -p scraper-service -- --ignored                # integration (needs Chrome)
cargo clippy -p scraper-service && cargo fmt              # lint + format
```

### Admin (bookmarkify-admin)
```bash
cd bookmarkify-admin
pnpm install
pnpm dev        # dev server, http://localhost:5777
pnpm build      # build (builds the @vben-core/* library deps first, then the app) → dist/
```

## Admin Panel (bookmarkify-admin)

`bookmarkify-admin/` has no per-service `CLAUDE.md`. Key points:

- **Framework:** a single flattened app generated by pruning vue-vben-admin down to the `web-ele` (Element Plus) template with the community `create-vben-admin` tool (see `vbenjs/vue-vben-admin#8037`) — no more Turborepo, no more `apps/web-ele/` nesting, no more antd/naive-ui/tdesign templates or deps. `src/`, `index.html`, `vite.config.mts` etc. live directly at `bookmarkify-admin/` root; `packages/` and `internal/` still hold the supporting `@vben/*` / `@vben-core/*` workspace libraries the app depends on.
- **No lint/test tooling, but `pnpm typecheck` is now a real gate.** The pruning tool drops `internal/lint-configs` and the Vitest setup entirely (single-app repos have no shared pipeline to lint/test against) — there is no `pnpm lint` or `pnpm test:unit` here anymore. Type checking used to report a constant **129 errors**, which meant it could never block anything and nobody read it; a genuine mistake in `src/` would have been invisible among them. Two changes fixed that on 2026-08-11: `src/element-plus-style.d.ts` declares element-plus's on-demand `.../style/css` subpaths (they are side-effect-only CSS imports that ship no `.d.ts`), which alone cleared **122** of the 129; and `scripts/typecheck.mjs` fails on `src/` errors only, printing the remaining 7 — all inside the vendored vben sources under `packages/` — without blocking. `src/` is now at zero, and the check runs in `deploy-admin.yml` before the build, mirroring the web workflow. `pnpm typecheck:raw` still gives the unfiltered vue-tsc output. Excluding `packages/` via tsconfig does **not** work: those files are pulled in by reference through the `@vben/*` workspace links, not by `include`.
- **API proxy:** In dev, Vite proxies `/api/admin` → strips the `/api` prefix → forwards to `http://localhost:8001`. So admin endpoints are `/admin/**` on the API.
- **Auth:** Uses Sa-Token `ADMIN` realm (separate from the `USER` realm used by the web frontend). Default credentials: `tcyeee@outlook.com` / `admin`.
- **No i18n.** The app removed `@vben/locales`/`setupI18n` entirely in favor of hardcoded Chinese strings; there's no app-level `src/locales`.
- **`.env` is gitignored** (holds `VITE_APP_TITLE` / `VITE_APP_NAMESPACE` / `VITE_APP_STORE_SECURE_KEY`) — CI supplies its own production values via `.env.production.local` in the deploy workflow.

## Cross-service contracts (what is generated vs. hand-maintained)

Two of the three seams in this system are pinned by tests; know which is which before editing types.

| Seam | How it is kept in sync |
|---|---|
| API ↔ scrapper (whole response) | `contract/scrape-response.sample.json`, deserialized by **three** suites (Rust `contract.rs`, Kotlin `ScrapeContractTest`, `SiteAssetIngestorTest`). Change either side without the other and all three go red. |
| API ↔ web/admin (**enums**) | Generated from the Kotlin enums into `bookmarkify-web/typing/enums.generated.ts` and `bookmarkify-admin/src/api/enums.generated.ts`. Regenerate with `cd bookmarkify-api && ./gradlew generateSharedEnums`; `SharedEnumContractTest` fails on drift. **Do not hand-edit the generated files, and do not re-declare an API-owned enum in either frontend.** |
| API ↔ web/admin (**VOs / interfaces**) | Still hand-copied — ~45 interfaces in `bookmarkify-web/typing/`, ~110 in `bookmarkify-admin/src/api/`. Nothing checks these. Adding a field to a VO requires editing both by hand, and forgetting produces no error, just a missing value at runtime. |

The enum half was done first because it is where a mismatch is most silent: `tsc` accepts a union
that is missing a member, so a newly added backend value falls through a `switch` and renders blank.
Frontend-owned enums (render modes, WebSocket message names, layout preferences) stay hand-written in
`typing/enum.ts` — the backend does not know about them.

## Service Interaction

```
Browser ──────────────────────────────────────────────────────────┐
  │                                                                │
  ▼ HTTP/WS                                                        │ Admin Panel (bookmarkify-admin)
bookmarkify-web ──── REST+WS ────► bookmarkify-api ◄── REST+WS ───┘
(Nuxt, port 3000)    satoken       (Spring Boot, :8001 local / :7001 prod)
                     header         │
                                    ├── PostgreSQL (database: bookmarkify, schema: public)
                                    ├── Redis (session/cache)
                                    ├── @Async executor (in-process parsing)
                                    └── POST /scrape ──► bookmarkify-scrapper
                                                         (Rust, port 3000)
```

Key flows:
- **Adding a bookmark:** Web → API stores a `BOOKMARK_LOADING` placeholder → publishes a Spring `ApplicationEvent` → an `@Async` listener triggers `/scrape` on the scrapper → result saved and pushed to the browser via WebSocket (`HOME_ITEM_UPDATE`).
- **Auth:** Every visitor gets an anonymous session via `/auth/track`. The `satoken` cookie/header is used on all requests — not `Authorization`. Registered users "upgrade" the anonymous session.
- **Storage:** Files (avatars, icons, social images, screenshots) go to Alibaba Cloud OSS. The bucket is **private-read** — what's stored in the DB is an **object key**, never a usable URL, so anything served to a browser must go through **`OssUtils.signAsset`**, which signs it and applies the per-display-mode resize. `signAsset` also accepts the legacy full URLs still present in older `site_asset` rows. The scrapper writes bytes but owns none of this: it returns `storageKey`, and the domain / signing / resizing are all API policy — see `docs/oss-architecture.md`.
- **Object governance:** every object in the bucket is tracked in the `oss_object` ledger, and every referrer (`user_info.avatar_file_id`, `background_image.file_id`, `site_asset.file_id`) stores a **ledger id, not a key** — so the key layout can change without touching business tables. A daily reconciliation sweep diffs bucket ↔ ledger ↔ referrers to find orphans. Read `FILE-SYSTEM-REFACTOR.md` before touching anything that writes to or deletes from OSS; in particular, **adding a new referrer requires updating `OssReconcileServiceImpl.collectReferencedKeys`** — miss it and those objects get classified as orphans.

## Site Assets & the Scrapper Contract

This is the part of the system most likely to be misunderstood, so read it before touching anything under `site_asset`, `AssetRolePolicy`, or the scrapper's `contract.rs`.

### The one rule

> **The scrapper reports facts (what the page declared). The API applies policy (what those facts mean for Bookmarkify).**

Concretely, the scrapper's response contains `extractor` — *which tag/field this image came from* — and **never** `role`. "Does an `apple-touch-icon` count as a LOGO?" is a Bookmarkify judgement, not a property of the web page. That mapping lives in one file (`server/asset/AssetRolePolicy.kt`), so changing the rules needs no scrapper change and no re-crawl.

| Concept | Owner | Example values |
|---|---|---|
| `extractor` (fact — where it came from) | scrapper | `LINK_ICON`, `APPLE_TOUCH_ICON`, `MANIFEST_ICON`, `JSON_LD_ORG_LOGO`, `OG_IMAGE`, `SITE_API_COVER` |
| `role` (policy — what we use it for) | API | `FAVICON`, `LOGO`, `SOCIAL`, `SCREENSHOT` |
| `quality` (policy — how much we trust it) | API | `TRUSTED`, `DEGRADED` |
| `storageKey` (fact — where the bytes landed) | scrapper | `scrapper/asset/<sha256-of-bytes>` |
| the URL a browser gets (policy — domain, signature, resize) | API | `OssUtils.signAsset` |
| `/ping`'s `{reachable, status, blocked}` (fact — what the probe saw) | scrapper | `status: 404` |
| whether that counts as dead (policy) | API | `LivenessPolicy.outcomeOf` |

The `/ping` row is the same rule again, and it was violated until 2026-08-06: the endpoint
returned `alive = status < 500`. Besides putting a Bookmarkify judgement in Rust, collapsing
the status code that way reported **404/410 as alive** — deep-link rot, the most common way a
bookmark actually breaks, was structurally invisible. Details in `bookmarkify-api/CLAUDE.md`
› Liveness sweeps.

The last row is the same rule applied to storage: the scrapper reports *which key it wrote*, never a
usable URL. Domain, presigning and per-mode resizing are the API's deployment concerns and would
otherwise leak into a service that has no business knowing them. See `docs/oss-architecture.md`.

### Data model

Four tables (`deploy/migrations/2026-07-29_site_assets_and_scrape_snapshot.sql`), replacing the old `bookmark_logo`:

| Table | Holds | Written by |
|---|---|---|
| `scrape_snapshot` | The full scrapper response as `jsonb` | crawl |
| `page_meta` | title / description / `site_name` / `site_short_name` / per-field `meta_sources` | crawl |
| `site_asset` | **One row per image** — role, extractor, quality, dimensions, `content_hash` | crawl |
| `site_display_pref` | Human-tuned padding / bg colour / pinned asset, keyed by **(bookmark, display_mode)** | humans only |

The crawl path (`SiteAssetWriter`) writes the first three and **never touches `site_display_pref`** — that separation is the whole point. The old `bookmark_logo` mixed crawl facts, file metadata, and human preferences in one row, so every re-crawl had to do a careful partial update to avoid clobbering an admin's settings.

`scrape_snapshot` exists so a field we didn't project into a column today can be **backfilled later without re-crawling**.

### Two display modes, inverted priorities

A bookmark renders two ways, and they want *opposite* things:

| | `TILE` (big icon + short name) | `LIST` (small icon + full name) |
|---|---|---|
| Asset priority | `LOGO` → `FAVICON` | `FAVICON` → `LOGO` |
| Text | `site_short_name` (manifest `short_name`) | `title` |
| Padding / bg colour | applies | effectively invisible |
| OSS resize | 256px | 64px |

This is why there is no single global "primary image" flag — `is_primary` is scoped *within* a role. It's also why `site_display_pref` is keyed by display mode.

The W3C already models this split: Web App Manifest has both `name` and `short_name`, the latter existing precisely for space-constrained icon captions.

### The monogram fallback

`content_hash` (SHA-256 of the image bytes) is what makes this possible: if a site's "LOGO" has the same hash as its favicon, it has no real logo — it just reused the icon under a different `rel`. `AssetRolePolicy` downgrades it to `DEGRADED`, and `shouldFallbackToMonogram()` tells the frontend to render a letter tile instead of upscaling a 32px favicon to 72px (which looks terrible).

### Field-level provenance

`page_meta.meta_sources` records the origin of **each field separately**:

```json
{ "title":       { "extractor": "OG",        "rawKey": "og:title" },
  "description": { "extractor": "META_NAME", "rawKey": "description" } }
```

The old single `source` column was actively wrong: the OG branch fell back to `meta[name=description]` for the description while still reporting `"og"` for the whole record.

### The contract is pinned by a shared fixture

`contract/scrape-response.sample.json` is deserialized by **three** test suites — Rust `contract.rs`, Kotlin `ScrapeContractTest`, and Kotlin `SiteAssetIngestorTest`. Change the contract on either side without updating the other and all three go red. Keep these in sync:

```
bookmarkify-scrapper/crates/scraper-service/src/contract.rs   ← Rust side
bookmarkify-api/.../entity/dto/scrape/ScrapeContract.kt       ← Kotlin side
contract/scrape-response.sample.json                          ← shared fixture
```

Wire format is camelCase with `SCREAMING_SNAKE_CASE` enums. The **request** body uses `deny_unknown_fields` — a misspelled field is rejected with 422 rather than silently defaulting.

### Where things live

```
bookmarkify-scrapper/crates/scraper-service/src/
├── contract.rs    # request/response types — the only cross-service coupling surface
├── scraper.rs     # Layer 1 HTTP fetch + SSRF primitives (manual redirect following)
├── headless.rs    # Layer 2 headless Chrome — returns rendered HTML, does not parse
├── extract.rs     # pure HTML → metadata/asset declarations (offline-testable)
├── siteapi.rs     # 站点官方 API 适配器 —— 全服务唯一的 host 特判，反爬救援用
└── pipeline.rs    # network enrichment: manifest fetch + image probe/download/upload

bookmarkify-api/.../server/asset/
├── AssetRolePolicy.kt       # extractor→role mapping + per-mode selection (pure, heavily tested)
├── SiteAssetResolver.kt     # DB-backed resolution + OSS signing/resizing (batch, avoids N+1)
├── SiteAssetIngestor.kt     # ScrapeResponse → rows (pure)
├── SiteAssetWriter.kt       # persistence (crawl facts only)
└── SiteDisplayPrefService.kt # human preferences only
```

### Gotchas

- **`assets.download` defaults to `PROBE`,** which *does* fetch the image body — `contentHash` and real pixel dimensions can't be computed otherwise. It just discards the bytes afterwards instead of storing them.
- **Admin "retry" must send `cache.mode = BYPASS`.** Otherwise it may hit the scrapper's cache and not actually retry.
- **⚠️ 无头抓取不要再用 spider 的 `Website::scrape()`（2026-08-09 重写为直接驱动 CDP）。** `scrape()` 是**爬虫**入口，产物是"这次爬行收获的页面集合"，而我们要的永远只是"这一页"；`with_limit(2)` 看似能把它掐成单页，实测不是：**种子页要等到爬虫接着抓了第二页才会进 `get_pages()`**。于是"抓不抓得到"取决于一件与目标站点毫不相干的事——渲染后的 HTML 里有没有同源可爬链接。生产实测 6/6 一致：chiphell / element-plus / rust-lang（有链接，日志里两条 `spider::utils: fetch`）全成功；`example.com`（唯一链接指向外域 iana.org）、`httpbin.org/html`（通篇没有链接）、`zjrljb.com` 全部返回 0 页，报 `HEADLESS_FAILED :: 没有返回任何页面`。同一时刻在同一个容器里 `chromium --headless=new --dump-dom` 抓同一个 URL 是好的（8s / 47KB），所以现场看起来像"无头浏览器很脆弱"，跟浏览器毫无关系。**这条规则专挑 SPA 空壳、单页工具站和深链下手，而它们恰恰是最需要 Layer 2 的一类。** 顺带，每次成功的抓取还白抓了一个我们根本不用的第二页（实测 3–11s，从 30s 预算里扣）。回归判据是 `headless.rs::page_without_any_link_still_returns_html`（本地服务器，无外部依赖）。
- **无头的两笔时间预算必须分开算：排队 ≠ 页面。** `HEADLESS_QUEUE_WAIT_SECS`（默认 20s）是等一个并发名额的上限，`HEADLESS_TIMEOUT_SECS`（30s）是拿到名额**之后**才开始计的页面预算。从前两者共用一个 deadline，后果在生产上很难看：2026-08-08 02:30 一批 8 条并发进来，除第一条外全部在排队里耗光 30s（耗时整齐地是 30014–30574ms），报出去却是"目标站点超时"，还顺手给这些 host 写了 24h 的无头熔断——同一个 chiphell.com 一分钟内先成功 16.4s、后超时 30s，站点没变，变的是队列。排队等不到名额报 `HEADLESS_UNAVAILABLE`，它既不写熔断也不写负缓存。
- **浏览器实例跨请求复用（`HEADLESS_BROWSER_TTL_SECS` 900s / `HEADLESS_BROWSER_MAX_USES` 50 后回收）。** 冷启动实测 11.6–14.7s，是 30s 预算里最大的一笔，而且从前每次抓取都要付。并发由信号量控制（`HEADLESS_CONCURRENCY`，默认 2），不再是"一次一个 Chrome"的全局互斥。**每个实例给一个独立的 profile 目录**：chromiumoxide 默认所有实例共用 `$TMPDIR/chromiumoxide-runner`，回收重开时新旧短暂并存会抢同一个 `SingletonLock`——老代码"启动前删锁文件"的做法等于在赌另一个实例不在用它。
- **`--disable-dev-shm-usage` 必须在启动参数里（`headless.rs::BASE_ARGS`，有断言守着）。** docker 默认 `/dev/shm` 只有 64MB，渲染进程共享内存耗尽时是**标签页直接消失**，而 cgroup 层面看不到任何 OOM 记录（生产上 `memory.events` 的 `oom_kill` 确实是 0）——这种失败没有任何症状。
- **截图的两个真实陷阱：** ① 不截图时才拦子资源（`BLOCKED_WHEN_NO_SCREENSHOT`，按 CDP `Network.setBlockedURLs` 走），要截图时整套放开——"这个页面长什么样"里当然包含它的样式与图片；**CSS 任何时候都不拦**，拦掉连布局都变了。② `ScreenshotParams.omit_background` 显式传 `Some(false)`：spider 时代它为 `None` 会去读 `SCREENSHOT_OMIT_BACKGROUND`，而该变量缺省兜底为 `true`（背景被抠成透明）。
- **截图"只截出裸 HTML"这个老 bug 是同一个根因，已随重写修好。** 症状是截出来的图没有 CSS、没有图片、没有 Web 字体，而 HTTP 200、字节数正常、`storageKey` 正常——**没有任何技术指标能发现它**，只有人眼能判，所以长期无人察觉。当年已排除资源拦截配置（三种取值下 stripe.com 的截图逐字节相同，都是 107264 字节），剩下的候选之一正是"spider 的 `scrape()` 路径不加载子资源"——现在看就是它：`scrape()` 收集的是爬虫抓到的页面，从来不是"我导航到这一页、等它渲染好、再截一帧"。改成直接驱动 CDP 后同一条命令截 stripe.com 得到 **287698 字节的完整渲染图**（Logo、渐变背景、品牌字体、下方厂商 Logo 墙都在）。这是 2026-08-09 在 macOS + Chrome 151 上的实测；生产是容器里的 chromium，机制相同但**上线后仍应人眼再看一次**：`headless.rs::screenshot_probe_writes_a_file_for_human_review` 会把图落到临时目录。
- **截图不进主解析链路。** 它强制走无头浏览器，放进主链路等于让每条新增书签排队等浏览器。改由解析成功后发 `BookmarkScreenshotEvent`，在 `BOOKMARK_SCREENSHOT_EXECUTOR`（**单线程**）上补抓，写入走 `SiteAssetWriter.upsertScreenshot` 而非 `persist` —— 后者会整体替换 PAGE 层资产，把主抓取刚写好的 SOCIAL 图一并删掉。（对端并发度已从"全局一个 Chrome"放宽到 `HEADLESS_CONCURRENCY`，这个单线程池是否跟着放宽是另一个话题，动之前先量截图的实际耗时。）
- **`AssetRolePolicy.resolve` 选图标，`resolveCover` 选封面，两者不能混。** 前者的 `roleOrder` 只排 LOGO/FAVICON，后者只排 SCREENSHOT/SOCIAL。把 SCREENSHOT 加进前者，一张 1280×720 的截图会因为"尺寸最大"在 TILE 模式下胜出，变成书签的图标。两个方向都有回归测试盯着。封面签名走 `OssUtils.signCover`（只限宽，`m_lfit`）——用图标那套等宽高的 `m_fill` 会把宽幅截图裁成正方形。
- **图标归 SITE 有一条例外：同一域名塞了多个互不相关产品时，图标改归 PAGE。** `tools.example.com/tools/random-avatar` 与 `/tools/glb-preview` 是两个产品，共用一张图标会让两个磁贴长得一模一样。Web 标准里表达这件事的是 manifest 的 `scope`（一个 origin 可以承载多个应用，各有各的 `name`/`icons`），但那要求站点正确声明、还得改跨服务契约；`AssetRolePolicy.divergesFromSite` 用**字节哈希**做同一个判断的事后版本 —— 真把子路径当独立产品做的站点，必然给它配了不同的图标。判据刻意保守：**本页声明的图标与站点现有图标毫无哈希交集**才算独立产品，部分重叠（共用 favicon、另外多带一张 apple-touch-icon）是普通站点的常态，按"有一张不同就算"去判会让几乎每条深链都误判，等于取消站点层。两侧都必须有可比的哈希，否则一律退回原行为。读取侧对应 `AssetRolePolicy.preferPageOwned`：页面图标存在时**筛掉**站点图标而不是与之竞争 —— 站点图标往往又大又 TRUSTED，混在一起按尺寸排序会把页面自己那张挤掉，整条链路白做。首页永远不参与这个判定（它就是站点本身）。**这条规则有个时序副作用**：深链先于首页被抓时，站点侧还没有图标，判定不成立，那批图标会经 `fillMissingAssets` 落到 SITE；等首页抓完把它们替换掉之后，要到该深链下一次重抓（30 天内容刷新）才会纠正过来。后台在书签详情的资产列表里用「本页专属图标」标签显示这一列，不下发 `ownerType` 的话这件事在后台无从查起。
- **The Layer 1 client must have both `redirect::Policy::none()` and `cookie_store(true)`.** The first is required for the manual per-hop redirect following that produces `fetch.redirectChain`; the second is required *because* of the first — plenty of sites hand out their anti-bot cookie on the 301 hop (bilibili's `buvid3`), and without a jar it is dropped before the next request. `scraper::fetch_html` also sends a full browser header set (`Accept`, `Accept-Language`, `Sec-Fetch-*`, `Sec-CH-UA`) and, when a sub-path is blocked with 403/406/412, warms up the origin root once to collect cookies and retries. Send only a UA and WAFs classify the request as a bot.
- **Navigations and subresources get *different* header sets.** `apply_navigation_headers` is for the page fetch; images and manifests go through `scraper::apply_subresource_headers` (`Sec-Fetch-Dest: image`/`manifest`, `no-cors`/`cors`, image/manifest `Accept`). Reusing the navigation headers would put `Sec-Fetch-Dest: document` on a PNG, which is itself a bot tell. The `Referer` on a subresource must be derived from the **page** URL via `scraper::referer_for` (browser-default `strict-origin-when-cross-origin`) — hotlink protection whitelists the referring site's domain, so pointing it at the asset's own host is the same as not sending it.
- **反爬状态码（403/406/412）在 AUTO 模式下会回退无头浏览器。** 根路径 cookie 预热救不回来时，Layer 1 已经把"伪装成浏览器"这条路走尽了，换成真浏览器才是换了个物种（B 站的 `/video/BVxxx` 就是这个场景）。关键约束：**无头导航若同样是非 2xx，必须拒收那份 HTML** —— 拦截页有标题有正文，收下就会变成一条标题叫"出错啦"的书签，比直接报错糟得多。这时报的是 Layer 1 的原始错误（现场更完整），并在 `detail` 里写明"已回退无头浏览器重试"。
- **反爬救援阶梯的第一级是站点官方 API（`siteapi.rs`），不是 Chrome。** 生产机实测：B 站根路径 200、内容页 412、而 `api.bilibili.com/x/web-interface/view` 200 —— 拒的是**机房出口 IP**，不是请求长相，所以根路径 cookie 预热、`finger/spi` 正牌指纹、乃至无头浏览器全都无效。API 只花几 KB 就拿到同一份标题/封面。这是全服务**唯一按站点特判**的地方，边界是：只报事实、只在常规抓取已失败后触发、出处如实记为 `SITE_API`/`SITE_API_COVER` 而绝不冒充 `OG`。新增站点适配器时若要加 `extractor` 取值，记得 `AssetRolePolicy.TABLE` 也要给它一条映射，否则那张图会被丢掉。
- **无头回退带一个按 host 的熔断（`ScrapeCache::headless_futile`，默认 24h，`HEADLESS_FUTILE_TTL_SECS` 可配）。** 回退失败一次就把整个 host 记下来，同站后续 URL 直接跳过。**只有关于目标页面的失败才进熔断**：无头导航拿到非 2xx（拦截页）、页面独占完整预算仍打不开（登录墙 SPA）算；`HEADLESS_UNAVAILABLE`（Chrome 起不来、CDP 挂了、并发名额等不到）不算——那是我方抖动，写进 24h 熔断等于让一次自家故障顺手拉黑一批本来抓得动的站点。同理它也不写 60s 负缓存，否则"我们现在忙"会被下一个调用方读成 `RECENTLY_FAILED`（E304，站点的结论）。没有它，一次全量重抓下几百条 B 站链接会各启一次 Chrome —— 反爬拒的是这台机器，不是那条路径，第一次就该得出结论。**TTL 必须长于调用方的巡检周期**：原值 900s 是照着「一次全量重抓」的时间尺度定的，而线上真实的重复请求由 API 侧的**小时级**巡检驱动（整点活性巡检、半点失活重试），15 分钟的熔断每次都已经过期，等于不存在。2026-08-07 查生产 `scrapper_call_log`：`console.cloud.tencent.com` 7 次调用 7 次失败，每次平均 28.6s，全烧在一个必然打不开的登录墙 SPA 上。回归测试 `headless_futile_ttl_outlives_an_hourly_sweep`。
- **抓取结果缓存默认 TTL 6h（`CACHE_TTL_SECS`），不是 1h。** 同一个原因：重复请求是巡检驱动的小时级形态，1h 的 TTL 每次刚好过期。2026-08-07 实测 449 次调用只覆盖 249 个 URL（200 次是重复抓取），而缓存命中只有 **2 次（0.4%）** —— 那个缓存当时等于不存在，只在占内存。上调不影响新鲜度：内容重抓周期是 30 天，一份 6 小时前的结果与刚抓的没有区别。
- **截不出图的页面要把「截不出」这件事记下来（`ParseLock.screenshot(pageId)`，TTL 35 天）。** `captureScreenshot` 的跳过条件是「已经有截图资产」，而失败时它什么也不写 —— 于是这个条件对失败页面**永远不成立**，每一轮内容重抓（默认 30 天）都要为同一个页面再付一次 30s 的无头。2026-08-07 查生产：297 个页面里只有 66 个有截图，其余每轮全在重试；而截图强制无头、对端 Chrome 全局串行、我方截图池单线程，代价是**串行**累加的（那 66 张成功截图本身就占掉了 21:12→21:48 整整 36 分钟）。TTL 取 35 天而非永久：站点改版、反爬策略调整、我方无头链路修好都可能让它变得可截。成功时调用方主动释放该 key，此后由资产存在性接管。
- **A non-2xx response is `ScrapeError::HttpStatus`, not `FetchFailed`** — "connected but rejected" and "never connected" need opposite debugging. Both still surface as the `FETCH_FAILED` wire code (the API's `classifyScrapperError` keys off it to mean "target site is unreachable"; a new code would be misread as *our* service failing). The diagnosis rides in `detail` (status, redirect chain, `Server`, the site's own error text, a what-to-check hint) and in `ErrorResponse.fetch`.
- **每加一个 scrapper 错误码，都必须回头看 `classifyScrapperError`。** 那个 `when` 的 `else` 分支是 E307「我方抓取服务不可用」，而 E307 有一个很重的副作用：`parseByApi` 会**刻意把书签留在 PENDING 不收口**（我方故障不该记成网站失联），于是用户桌面上那个节点要一直转到 30 分钟后 `drainStuckLoading` 的陈旧阈值到期。也就是说，漏掉一个属于目标站点的错误码，代价不是"分类不准"，而是"这条书签转圈半小时"。`RECENTLY_FAILED`（负缓存命中，60s TTL）就这么被漏了：它明明是站点的事实——scrapper 只在取回阶段失败时写负缓存，且排除了 `INVALID_URL`/`FORBIDDEN_TARGET`——同一网址被两个用户先后添加就会撞上。现已归入 E304。反方向的例子是 2026-08-09 新增的 `HEADLESS_UNAVAILABLE`：它与 `HEADLESS_FAILED` 只差一个词，含义却相反——后者是"这一页用浏览器也打不开"（站点的结论，可以判失联），前者是"我们现在打不开任何页面"（我方的状态，必须留在 PENDING 等下一轮）。落在 `else` 里本来也是 E307，仍然显式写一条分支，因为这个 `when` 的 `else` 太重要，不该靠"恰好落对了"。
- **只有域名才抓：`localhost` / `127.0.0.1` / 裸 IP 一律拒绝，三端各有一道门。** 这跟 SSRF 防护是两件事——SSRF 回答"会不会打到我方内网"（只拦私有段，公网裸 IP 放行），这条回答"这个目标是不是一个网站"。`http://47.97.71.143:8001/` 两个问题的答案相反：它不指向内网，但它是别人内网服务暴露在公网的端口，抓回来只会是一个登录页。三道门分别是 web 的提示（能收藏、但明说不抓）、API 的 `ScrapeTargetGuard`（拒绝时 E309，挡在 `ApiServiceImpl.scrape` / `pingWebsite` 这个唯一咽喉点上）、scrapper 的 `validate_target_is_domain`（在查缓存和发第一个字节之前）。**scrapper 这道门在两个端点上报法不同，且必须不同**：`/scrape` 回 403 `FORBIDDEN_TARGET`，而 `/ping` 回 200 + `blocked: true`。原因是发布顺序——线上那版 API 把 `FORBIDDEN_TARGET` 归进 E304「域名无法访问」，ping 路径据此判 **DEAD**，于是"新 scrapper + 老 API"的窗口里每一条 localhost / IP 书签都会被标成失联，恰好是这条规则要防的事；`blocked` 则是两版 API 都读成「无结论」的既有字段（`LivenessPolicy.outcomeOf` 第一条分支），两个方向都不需要部署顺序。语义上也对得上：`blocked` 说的是"本服务拒绝了这次探测"，"这不是个网站"与"这打到内网"同属这一类。回归测试 `ping_rejects_ip_literal_before_probing`。**判断必须落在 `ApiServiceImpl.scrape` 而不是各调用点**：`parseBookmarkExclusively` 早就按 `BookmarkLinkType` 过滤了，但后台的重新获取/一键更新/重抓资产/活性检测、截图补抓、调试抓取这六个入口一个都没带，2026-08-08 生产上那条 `http://127.0.0.1:5000/ → 403` 就是从其中之一漏出去的（代价不只是一次白跑：它还把那个页面的 `consecutive_fail` 推上去了一格）。相应地，`FORBIDDEN_TARGET` 从 E304 拆到了 E308——"站点打不开"是关于站点的结论，"我们不去打开它"是我方的决定，混在一起时 ping 路径会把后者判成失联，等于用一个策略决定给用户自家的服务判死刑。后台对这类书签收起全部抓取相关的卡片与按钮（`views/bookmark/linkType.ts`），因为它们的标题/图标/`page_meta`/巡检游标**永远**是空的，摆出来只会被当成抓取故障去排查。
- **The local Jsoup path (`parseLocally`) no longer produces images.** Only the scrapper path writes `site_asset`. Two parsers each writing their own icon model is exactly what this refactor removed.
- **`fetch.tls` and `diagnostics.robots` are deliberately omitted,** not populated with guesses — the underlying capability isn't implemented yet.
- **抓取落地在 https 时会把 `page.urlScheme` / `site.scheme` 从 http 升上去（`ScrapeResponseExt.upgradedSchemeOf`），只升不降。** 这两列原本只在建行那一刻写过一次，取自用户当初提交的网址，此后从不回写 —— 一条当年用 `http://` 收藏、站点后来全站上了 https 的书签，会永远以 http 为抓取目标（`page.rawUrl` 是拿这一列拼的），每轮抓取和活性探测都先白吃一跳 301，后台的「协议」列和 `site.rootUrl` 也一直是错的；而终点一直躺在 `fetch.finalUrl` 里没人读。**能单独改 scheme 的前提是它不参与 page 的去重四元组**（`(siteId, urlPath, urlQuery, urlFragment)`），所以改它不会造出重复页面 —— 同理，`authority` 不一致时**一律不动**：`example.com` 跳到 `www.example.com` 说明这条记录指向的是另一个 host，那是 canonical 重定向的问题，顺手改 scheme 只会把「记错了地址」伪装成「记对了」。快照那一列存的仍是**本次实际请求出去**的地址（`parseByApi` 里的 `requestedUrl`），不是升级后的。回归测试 `ScrapeResponseApplyToTest`。
- **Table name prefixes mark the owning layer, not the feature area.** `site_` = one row per domain, `page_` = one row per canonical page, `user_`/`bookmark` = per user. No prefix = system-level (logs, config, ledgers). Before adding a table, answer the same question the layering itself is built on: *does this value change if you switch users? if you switch to another page on the same domain?* — the answer picks the prefix. This rule already existed implicitly (it is what `SiteEntity`'s class comment describes) but was never written down, so half the tables drifted off it: `site_page_meta` was keyed by page, `bookmark_sweep_log` had no bookmark in it at all, and `bookmark` itself meant *page* while users mean `bookmark_user_link`. Fixed by `2026-08-03_rename_three_layers.sql`.
- **新加一张按 `page_id` / `site_id` 归属的表，必须同时更新 `OrphanCleanupService`。** 后台「系统配置 › 书签清理」删的是**已无人收藏**的页面与站点（本地/IP，或已判定失活），级联删除的表名是在那个类里逐个列出来的 —— 库里没有一条外键约束（`deploy/schema.sql` 里只有 `background_config` 那两条），所以漏掉一张表不会报错，只会在库里留下一批永远找不到归属、也再没有任何入口能看见的行。这与 `OssReconcileServiceImpl.collectReferencedKeys` 是同一类陷阱，方向相反：那边漏登记会把还在用的对象**误删**，这边漏登记会把该删的行**留下**。清理只删数据库行，失去引用的 OSS 对象仍旧交给对账链路按宽限期回收 —— 那条路径有"分类不完整就不删"的闸门，绕开它自己删对象等于把保护一并绕开。
- **`2026-08-03_rename_three_layers.sql` needs a downtime window** — the only migration here that does. Table renames cannot be made backward-compatible in either direction, so the sequence is: stop the old instance → run the migration → start the new jar. Single-instance deployment makes that one container restart. It renames `bookmark`→`page`, `bookmark_user_link`→`bookmark`, `bookmark_ping_log`→`page_ping_log`, `bookmark_category`→`page_category`, `bookmark_sweep_log`→`sweep_log`, `site_page_meta`→`page_meta`, plus every `bookmark_id` column that pointed at a page → `page_id`, plus the index and constraint names (`ALTER TABLE RENAME` does *not* carry those along, and leaving `bookmark_pkey` on a table called `page` recreates the exact incoherence being fixed). Kotlin side: `BookmarkEntity`→`PageEntity`, `BookmarkUserLink`→`BookmarkEntity`, and mappers accordingly. **Service-layer names deliberately keep "Bookmark"** (`IBookmarkService`, `BookmarkController`, `BookmarkShow`) — those describe the user-facing feature, which *is* bookmarks, so they were already correct.
- **Migrations are hand-applied** (`deploy/migrations/`, no Flyway) and the deploy workflow does *not* run them. Order matters: create tables → deploy → full re-crawl → only then the corresponding drop migration.
- **`2026-08-03_site_layering_cleanup.sql` must be applied *after* deploying the API** — the opposite direction from every other migration here, which is exactly why it is easy to get wrong. It drops `page.nsfw` / `nsfw_reason`; the running old code still reads them, so applying it first makes every scrape throw. The window between deploy and migration is safe (new code stops writing that column, and all reads already went to `site.nsfw`). Its header carries the four pre-flight counts to re-check in any other environment. It deliberately does **not** touch `page.app_name` — that column looks legacy but is still live across API, admin and web (see `SITE_LAYERING_DESIGN.md` §9), so dropping it is a feature migration, not a cleanup.
- **Removing a column that `BookmarkAdminVO` reads is silent.** That VO is built with `BeanUtil.copyProperties`, so a dropped source property does not fail — the field just stays at its default forever. Dropping `page.nsfw` this way would have made the admin panel unable to flag any NSFW site, with no error anywhere. `nsfw` is now explicitly backfilled from `site` in `adminListAll` / `adminDetail`; do the same for any future column that moves layers.
- **`2026-08-03_index_and_constraint_hardening.sql` is deploy-order-free.** Pure index/constraint additions (`user_info` email+github uniqueness, `user_preference`/`background_config` per-uid uniqueness, several missing uid indexes, `site_display_pref.site_id NOT NULL`). All `CONCURRENTLY` and idempotent, safe to re-run.
- **`2026-08-06_liveness_sweep_hardening.sql` should be applied *before* deploying the API.** It creates `sweep_log`, which every sweep round writes to. The insert is wrapped in `runCatching`, so a missing table only produces `warn` lines and the sweeps still run — but that table *is* the only durable record of a breaker trip, so a late migration means a silent hole exactly where the evidence matters. It also swaps `idx_bookmark_next_check` for `idx_page_due_check`, which the new candidate query is written against (missing it costs a seq scan per round, not correctness), and pushes existing `ARCHIVED` rows' cursors onto the new 30-day revival cycle.
- **`2026-08-07_config_change_log.sql` should be applied *before* deploying the API.** It creates `config_change_log`, written from `JsonConfigAccessor.update()` — the single choke point through which every `system_config` write passes. That insert is wrapped in `runCatching` too, so a missing table only warns and the configuration still saves; what a late migration costs is the evidence for "who changed this parameter, and to what", which is the only question that table exists to answer and the only one `system_config` (current value + `update_time`, no operator, no history) cannot. Pure `CREATE ... IF NOT EXISTS`, safe to re-run.
- **`2026-08-08_sweep_log_observability.sql` should be applied *before* deploying the API.** It adds `sweep_log.batch_size` and `sweep_log.short_circuited_dead`; the new code writes both on every round, and `recordSweepRound` is wrapped in `runCatching`, so missing columns cost a warn line and **every** round record in that window — the same data the 常驻告警条 reads to answer "巡检还在跑吗". Both columns are deliberately **nullable with no default**: pre-2026-08-08 rows genuinely lack the information, and `0` would be read as "上限为 0" / "短路里一条 DEAD 都没有", both false. The admin panel branches on `null` to fall back to the old presentation. Why they exist: `backlog > candidates` is *not* a valid "积压追不上" judgement — `candidates` also has non-domain bookmarks (local/IP) filtered out of it, so one such bookmark makes the inequality permanently true; the real threshold is `batchSize`, which differs per task (50 / 200) and belongs on the row rather than hardcoded in the frontend. `short_circuited_dead` splits `dead_count`/`unknown_count`, which are the **探测 + 站点层短路复用** total, from the breaker's denominator, which counts only 真正探测过的 rows.
- **`2026-08-09_ping_log_sweep_id.sql` must be applied *before* deploying the API — this one harder than the rest of the batch.** It adds `page_ping_log.sweep_id`, which links a 巡检轮次 to the探测 it produced, so the admin panel can drill from one `sweep_log` row into the pages it actually probed. Unlike `recordSweepRound`, the ping-log insert is **not** wrapped in `runCatching` (that batch of results is the only evidence for "我方哪里坏了"; swallowing the exception would throw the现场 away too) — so a missing column doesn't cost a column, it aborts the whole round: results unpersisted, `next_check_at` unadvanced, `recordSweepRound` never reached, and the 常驻告警条 reporting "巡检已 N 小时没跑过". The column is nullable with no default; pre-migration rows genuinely belong to no known round, and the drill-down says so explicitly rather than rendering an empty list. **Why not a time window instead:** `sweep_log.create_time` is the round's *end* (minus `duration_ms` gives the start), but the two sweep tasks lock independently of each other with a 30-minute TTL, so a slow round overlaps the next task's window — and `page_ping_log` has no `task_label` to separate them. **The sweep↔`scrapper_call_log` edge stays a time-window approximation on purpose:** a sweep's probes go to `/ping`, which writes *nothing* to `scrapper_call_log` (only `/scrape` does, via `ApiServiceImpl.logScrapperCall`), and the re-crawls a sweep triggers are dispatched asynchronously with neither a round id nor a page id on the row. Don't "fix" that by logging `/ping` into `scrapper_call_log`: it would change that table's meaning from 抓取调用 to scrapper 一切调用 and bury the actual fetch failures under an order of magnitude more rows — the probe's现场 already lives in `page_ping_log`.
- **`2026-08-10_scrapper_call_log_error_code.sql` should be applied *before* deploying the API.** 它给 `scrapper_call_log` 加 `error_code` 与 `target_status`。写入包在 `runCatching` 里，列不存在只会打一行 warn —— 但那是**整行 insert 失败**，不是缺两列，代价是整段窗口里一条抓取调用日志都不落。两列的分工是这次改动的全部理由：已有的 `http_status` 记的是 **scrapper 回给我方**的码（`FETCH_FAILED` 恒 502、`TIMEOUT` 恒 504），跟目标站点无关；而「403/406/412 被反爬拦下」和「连不上/DNS 挂了」要完全相反的处置，分得开它们的只有目标站点自己的状态码，它一直躺在错误响应的 `fetch.httpStatus` 里没人读。`error_code` 同理：这个码早就被 `classifyScrapperError` 用着了，只是没存下来，于是「这个站点败在哪一类」事后只能去 `error_msg` 那段自由文本里用 LIKE 猜。两个值另有两个**我方自造**的取值（`SCRAPPER_UNREACHABLE` / `CONTRACT_MISMATCH`），标记「压根没拿到 scrapper 的回答」，它们不属于 scrapper 契约 —— 后台按站点聚合时要把这类排除在归因之外，否则一次我方故障会被读成一批站点抓不动。配套的后台页是「第三方管理 › Scrapper失败站点排行」（`/admin/scrapper-call-log/failed-host-ranking`，不分页），它刻意**只呈现事实、不给"建议屏蔽"**：同一个高失败率对应的处置可能是写站点 API 适配器、交给巡检判失联、或者根本不该按站点归因。
- **The `/ping` contract change in that same batch is deploy-order-free, in both directions.** The scrapper still emits the legacy `alive` field and the API still reads it when `reachable` is absent, so either service can ship first. Both halves of the shim are marked for deletion once the rollout settles — see `PingResponse` on each side.
- **`2026-08-05_bookmark_flow_hardening.sql` must be applied *before* deploying the API.** It adds `bookmark.dispatch_attempts`, which `drainStuckLoading` reads every 30 seconds — deploy first and that sweep throws on every tick, i.e. bulk imports never finish and every lost parse event stays lost. It also adds the indexes that the add-bookmark path depends on (`bookmark` and `user_layout_node` previously had **no secondary indexes at all**, so `drainStuckLoading` was doing a full table scan twice a minute) and the `uk_bookmark_uid_page` unique index that now backs duplicate detection. The duplicate-repair step inside it is destructive by design: it keeps the earliest link per `(uid, page_id)` and deletes the extra tiles, which is E126's semantics applied retroactively — without it the unique index cannot be created.
- **`deploy/schema.sql` is the schema of record** — a full snapshot of what the database currently looks like, *not* a migration. It exists because the one-off scripts under `deploy/migrations/` get pruned periodically (they are change records, and clearing them is fine), but "the current structure" must not disappear with them: without it a new environment cannot be stood up, nothing can be reproduced locally, and indexes/constraints are unreviewable. **Refresh this file after any structural change**; it should always run cleanly against an empty database. Regenerate with `pg_dump --schema-only` where available (a `pg_catalog`-based reconstruction script was used to seed it).
- **`2026-08-02_file_id_indirection.sql` must be applied *before* deploying the API.** The new code reads `oss_object` and no longer reads `user_file` — deploying first turns every avatar and background image blank. `2026-08-03_oss_object_hash_unique.sql` is the opposite: it must wait until *after* a full re-crawl has moved every asset onto content-addressed keys, and it fails loudly with a pre-check rather than half-applying.
- **The 2026-07-30 batch must be applied *before* deploying the API** — the new code reads columns that don't exist yet (`page.next_check_at`, `page.locked_fields`, `page_ping_log.outcome`). Run `2026-07-30_missing_table_ddl.sql` first (it only fills in `CREATE TABLE IF NOT EXISTS` for tables whose DDL was never committed), then `_ping_outcome`, `_bookmark_check_schedule`, `_bookmark_locked_fields`. All are idempotent.
- **`2026-07-31_ai_call_log.sql` should be applied before deploying the API.** Every DeepSeek call now writes a row to `ai_call_log`; a missing table only produces `warn` lines (the insert is wrapped in `runCatching`, business logic is unaffected) — but that is exactly the audit trail the table exists for, so a late migration means a silent hole in the history.
- **Sibling `CLAUDE.md` files carry the details:** the liveness sweep contract (tri-state ping, breaker, `next_check_at`, backoff, field locks) is in `bookmarkify-api/CLAUDE.md` under "Liveness sweeps".

## Local Dev Port Conflict

Both `bookmarkify-web` and `bookmarkify-scrapper` listen on port **3000**. You cannot run them simultaneously without remapping one. In production, Nginx routes traffic so they never bind on the same host. For local development, either run only one at a time or override the scrapper port via the `PORT` environment variable (`PORT=3001 cargo run -p scraper-service`).

## Infrastructure (deploy/)

`deploy/compose.yml` — Docker Compose for the full stack; every secret is a `REPLACE_FLAG` placeholder that must be substituted manually before use. `deploy/nginx/` — reverse-proxy config (`bookmakify.cc.conf`, `admin.bookmarkify.cc.conf`, `file.bookmakify.cc.conf`).

## Deployment (CI/CD)

All four services deploy via GitHub Actions (`.github/workflows/deploy-{api,web,scrapper,admin}.yml`), **triggered on push to the `prod` branch** (or manual `workflow_dispatch`), each path-filtered to its own directory. `main` is the working branch; deploys happen by promoting to `prod`. Concurrency guards prevent overlapping deploys, and WeChat/Server酱 notifications fire on success/failure. Target host: `ubuntu@123.206.216.124`.

- **API & scrapper:** compiled on the GitHub runner (JVM fat jar / Rust binary via a Docker `export` build stage), relayed to the server through Aliyun OSS, then assembled into a thin runtime Docker image and started via Compose. This deliberately avoids a direct cross-border `docker push` to Tencent TCR, which used to take ~30–40 min from GitHub runners — **TCR is no longer used for either service.**
- **Web & admin:** static builds (`nuxt generate` / Vben `build`) rsynced directly to nginx-served directories on the server — no Docker involved.
